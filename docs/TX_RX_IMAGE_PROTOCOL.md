# NRF_TX ↔ NRF_RX 图像无线协议

本文档是当前工程图像无线链路的正式协议说明，以现有 `nrf_tx`、`nrf_rx` 源码为准。

## 1. 协议边界与公共规则

链路为：`摄像头 → NRF_TX → 2.4 GHz Radio → NRF_RX → UART3 → STM32 → PC`。

- 本文只定义 `NRF_TX ↔ NRF_RX` 的图像无线包。
- 无线图像包不使用 `5A 41 59 53`（ZAYS）头，也不使用旧版 `IMG` ASCII头。
- Radio有效载荷固定254字节；胶囊SN固定8字节。
- RX解包缓冲保留20000字节防御上限；当前TX只允许发送不大于19252字节的CX93510原始JPEG图像块。DATA头12字节，单片最多携带242字节JPEG。
- 所有16位协议字段均为大端（高字节在前）；发送前整包清零。
- 帧ID为1字节，当前程序按0～254循环。
- Radio硬件CRC16配置：初值`0xFFFF`，多项式`0x11021`。

```text
packet_count = (jpeg_length + 241) / 242
```

## 2. BEGIN（0x01）

方向：`NRF_TX → NRF_RX`。每帧首次发送时连续发送2次。

| 偏移 | 长度 | 字段 | 定义 |
| --- | ---: | --- | --- |
| 0 | 1 | CMD | `01` |
| 1 | 1 | Frame ID | 图片编号 |
| 2～9 | 8 | Capsule SN | 胶囊序列号 |
| 10～11 | 2 | JPEG Length | JPEG总长度，大端 |
| 12～13 | 2 | Packet Count | DATA分片总数，大端 |
| 14～16 | 3 | Version | 主、次、测试版本号 |
| 17 | 1 | Accel Valid | `01`表示本帧XYZ有效；`00`表示采样失败，XYZ不可使用 |
| 18～19 | 2 | Accel X Raw | ADXL362 X轴原始值，16位有符号二补码，大端 |
| 20～21 | 2 | Accel Y Raw | ADXL362 Y轴原始值，16位有符号二补码，大端 |
| 22～23 | 2 | Accel Z Raw | ADXL362 Z轴原始值，16位有符号二补码，大端 |
| 24～253 | 230 | Reserved | `00` |

RX只接受：已经绑定SN、包内SN与绑定SN一致、长度为1～20000，且分片数与长度计算结果一致的BEGIN。

### 2.1 TX图像长度上限

STM32继续使用TYGD31旧版20064字节固定记录，其中128字节为DeviceInfo，完整JPEG最多占19936字节。CX93510的`0x10`图像块不含DQT/DHT，STM32会用686字节标准头替换原始的2字节SOI，因此TX可发送的原始图像上限为：

```text
19936 - 686 + 2 = 19252 bytes
```

TX在图像采集完成后、分配Frame ID和启动Radio之前检查该长度。超过19252字节的帧不发送BEGIN/DATA/END，不等待ACK，并在启用TX运行日志时输出`[IMAGE] rejected before RF`。RX保留20000字节检查仅作为异常包防护，不代表TX可以发送超过19252字节的帧。

当前CX93510使用折中压缩档：`JPEG_ENC_DCT_LM=0x00`、`JPEG_ENC_DCT_CH=0x03`。亮度分量保留低压缩以维持轮廓和纹理清晰度，色度分量使用高压缩以减少图像大小。该设置不改变480×480分辨率或无线包格式。

### 2.2 ADXL362原始数据说明

- TX在补光预热结束后、调用`cx93510_capture_one()`触发图像采集之前，立即读取一次ADXL362完整数据寄存器，并把该次采样的X/Y/Z绑定到随后生成的同一Frame ID及BEGIN包。
- 为降低功耗，ADXL362平时处于standby。每个图像周期开始时，它与摄像头同步进入100Hz测量；复用现有25ms补光/摄像头预热时间产生新样本，读取后立即回到standby，不额外增加图像周期等待时间。
- TX只传原始寄存器值，不在发送端换算mg、不计算合加速度、角度或水平/竖直姿态。
- X/Y/Z均为16位有符号二补码，高字节在前。例如`X=-930`编码为`FC 5E`。
- 当前量程为`+-2 g`；正常模式典型灵敏度约为`1 mg/LSB`，但该比例只供RX或上位机换算，精确结果需要校准。
- `Accel Valid=00`时，接收端必须忽略三个XYZ字段，不能把其中的零值解释为真实加速度。
- BEGIN仍为固定254字节，因此该扩展不改变DATA载荷、分片数量、END校验或Radio硬件配置；旧RX会把17～23当作保留字节忽略。

## 3. DATA（0x80）

方向：`NRF_TX → NRF_RX`。

| 偏移 | 长度 | 字段 | 定义 |
| --- | ---: | --- | --- |
| 0 | 1 | CMD | `80` |
| 1 | 1 | Frame ID | 必须与BEGIN一致 |
| 2～9 | 8 | Capsule SN | 必须与BEGIN及RX绑定SN一致 |
| 10～11 | 2 | Fragment Index | 大端，从0开始 |
| 12～253 | 242 | JPEG Data | JPEG分片数据 |

普通分片携带242字节。最后一片只取JPEG剩余有效字节，包尾补`00`且不计入整图校验。RX使用分片位图去重；相邻DATA当前间隔1ms。

## 4. END（0x03）

方向：`NRF_TX → NRF_RX`。

| 偏移 | 长度 | 字段 | 定义 |
| --- | ---: | --- | --- |
| 0 | 1 | CMD | `03` |
| 1 | 1 | Frame ID | 必须与BEGIN一致 |
| 2～9 | 8 | Capsule SN | 必须与BEGIN及RX绑定SN一致 |
| 10 | 1 | Image Checksum | 全部有效JPEG字节累加取低8位 |
| 11～253 | 243 | Reserved | `00` |

```text
checksum = (jpeg[0] + jpeg[1] + ... + jpeg[length-1]) & 0xFF
```

RX只有在所有分片到齐且整图校验通过后才发送ACK，并向STM32转发完整图片。分片不全时不应答但保留当前接收状态；校验失败时丢弃本帧。

## 5. ACK（0x10）

方向：`NRF_RX → NRF_TX`。RX连续发送2次。

| 偏移 | 长度 | 字段 | 定义 |
| --- | ---: | --- | --- |
| 0 | 1 | CMD | `10` |
| 1 | 1 | Frame ID | 成功接收的图片编号 |
| 2～9 | 8 | Capsule SN | 成功接收图片的SN |
| 10～253 | 244 | Reserved | `00` |

TX只接受Frame ID和当前SN均匹配的ACK，避免旧ACK或其他胶囊的ACK结束当前等待。

## 6. 超时和重发

1. 首轮发送：`BEGIN × 2 → DATA[0...N-1] → END`。
2. 首轮END后等待ACK 30ms。
3. 超时最多重试1次。
4. 重试发送全部DATA和END，不重发BEGIN。
5. 当前重试END发完后结束本帧，不再等待第二轮ACK。

为降低TX功耗，启动SN配置窗口结束后Radio不再持续处于RX：普通SN广播、BEGIN和DATA发送完成后均回到Disabled；首轮END发送完成后才打开RX并保持最多30ms等待ACK，收到匹配ACK或发生超时后立即关闭。运行阶段因此不再支持任意时刻下发控制命令。

RX在END到达但分片不全时保留接收状态，等待重发的DATA；下一次END再触发完整性和校验检查。

## 7. 完整示例

SN=`59 62 60 90 11 00 00 00`，JPEG长度16454（`0x4046`），共68片（`0x0044`），Frame ID=`BD`，版本1.1.0：

```text
BEGIN:
01 BD 59 62 60 90 11 00 00 00 40 46 00 44 01 01 00 01 02 08 FF 14 FC E8 [补00至254字节]

DATA #0:
80 BD 59 62 60 90 11 00 00 00 00 00 [JPEG第0～241字节]

DATA #67（最后一片）：
80 BD 59 62 60 90 11 00 00 00 00 43 [最后240个有效字节] 00 00

END:
03 BD 59 62 60 90 11 00 00 00 CS [补00至254字节]

ACK:
10 BD 59 62 60 90 11 00 00 00 [补00至254字节]
```

`CS`必须用16454个JPEG有效字节实际计算。

示例BEGIN的加速度扩展表示：有效，`X=0x0208=520`、`Y=0xFF14=-236`、`Z=0xFCE8=-792`。

## 8. 与0x81的关系

无线协议完成于RX校验END并发出0x10 ACK。之后RX在本地构造UART帧：

```text
FF 55 12 34 + 81 + DataLength(H,L) + 128字节设备信息 + JPEG + Checksum
```

STM32再改用`5A 41 59 53`头转发给PC。`0x81`不是254字节Radio包，不能作为TX端无线测试包发送。

这128字节不是RX和STM32各生成一份，而是同一份`DeviceInfo`逐级补齐：

1. RX从图片BEGIN提取TX版本、SN和ADXL原始值；从本机提取RX版本、芯片ID、天线、频点和RSSI。
2. STM32收到后保留上述字段，再补入STM版本、芯片ID、运行时间、最终JPEG长度和RTC。
3. 没有定义或尚未采集的保留字段写0。

固定字段如下：

| DeviceInfo偏移 | 长度 | 字段 | 格式 |
| ---: | ---: | --- | --- |
| 0～4 | 5 | 设备信息标识 | 固定`00 55 AA 88 99` |
| 5～6 | 2 | TX版本 | 主版本、子版本，各1字节 |
| 7～8 | 2 | RX版本 | 主版本、子版本，各1字节 |
| 9～10 | 2 | STM版本 | 主版本、子版本，各1字节 |
| 11～18 | 8 | 胶囊SN | 来自0x05广播并由图片BEGIN再次确认 |
| 19～26 | 8 | RX芯片ID | nRF52832 `FICR.DEVICEID[0..1]`内存字节序 |
| 27～38 | 12 | STM芯片ID | STM32 96位唯一ID |
| 39～44 | 6 | ANT1～ANT6 RSSI | nRF `RSSISAMPLE`幅值；例如40表示约-40 dBm，0表示无样本 |
| 45～47 | 3 | STM运行时间 | 秒，低字节在前 |
| 49 | 1 | 当前天线 | 1～12 |
| 50 | 1 | Radio频点 | MHz偏移量；10表示2410 MHz |
| 51～56 | 6 | ANT7～ANT12 RSSI | 格式同ANT1～ANT6 |
| 61 | 1 | TX测试版本 | 1字节 |
| 62 | 1 | RX测试版本 | 1字节 |
| 63 | 1 | STM测试版本 | 1字节 |
| 65～67 | 3 | STM最终JPEG长度 | 字节数，低字节在前 |
| 70～76 | 7 | STM RTC | 延续TYGD31旧工程顺序 |
| 83～89 | 7 | 上次RTC/保留 | 当前未写入时为0 |
| 90 | 1 | Accel Valid | 与BEGIN字节17一致 |
| 91～92 | 2 | Accel X Raw | 16位有符号二补码，大端 |
| 93～94 | 2 | Accel Y Raw | 16位有符号二补码，大端 |
| 95～96 | 2 | Accel Z Raw | 16位有符号二补码，大端 |

RX只负责保存和转发原始值，不进行姿态算法处理。STM32或PC读取时先检查`DeviceInfo[90] == 1`，再按大端有符号16位解析XYZ。

RX到STM32的0x81帧校验和为`DeviceInfo[0..127] + JPEG全部有效字节`的8位累加和。旧实现只校验JPEG，不能发现SN、ID或天线信息损坏；因此RX和STM32固件必须配套更新。STM32转发PC时仍保持旧工程顺序：`5A 41 59 53 81 + Length + JPEG + DeviceInfo + Checksum`。
