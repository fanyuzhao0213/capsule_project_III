# OV7676 + CX93510 + nRF52832 图像采集与传输说明

## 1. 系统目标

摄像头发送板使用 OV7676 输出并行 YUV422 图像，由 CX93510 完成 JPEG 压缩和帧缓冲管理，再由 nRF52832 将 JPEG 拆成固定长度无线包发送。专用接收板收到无线包后，通过 1 Mbps UART 原样转发给 STM32；STM32校验并透传到电脑；Qt程序完成去重、分片重组、JPEG合成、保存和显示。

当前默认参数：

- 图像尺寸：480 x 480。
- OV7676输出：YUV422，字节顺序 Y0/U/Y1/V。
- JPEG模式：CX93510直接帧，标准量化表，低压缩率/高画质。
- 图像采集请求周期：250 ms。
- 每个配置块和JPEG块默认只发送一遍。
- 无线频率：2400 MHz。
- 无线速率：Nordic 1 Mbit。
- 无线发射功率：nRF52832最高的 +4 dBm。
- 固定无线包长度：254字节。
- 串口：1,000,000 baud、8N1、无硬件流控。

## 2. 数据链路

```text
OV7676
  |  DVP: PCLK/VSYNC/HSYNC/D0..D7，YUV422
  v
CX93510
  |  JPEG压缩 + 内部帧缓冲
  |  SPI读取
  v
nRF52832摄像头发送板
  |  2400 MHz，1 Mbit，254字节固定Radio包
  v
nRF52832专用接收板
  |  UART TX=P0.15，1 Mbps
  v
STM32 USART2 RX=PA3
  |  DMA循环接收 + CRC16校验
  |  USART1 TX=PA9，1 Mbps
  v
电脑Qt程序
  |  CRC校验、去重、分片重组、JPEG合成
  v
显示并保存.jpg文件
```

## 3. 工程角色选择

`app_role.h`中的宏决定同一个nRF工程编译成哪种板卡角色：

```c
#define APP_ROLE_DEDICATED_RECEIVER 0
```

- `0`：摄像头发送板，初始化SPI、CX93510和OV7676，采集并发送图像。
- `1`：专用接收板，不初始化摄像头相关外设，只开启Radio、P0.23模式控制和UART桥接。

摄像头板与接收板必须使用相同的无线频率、地址、速率、固定包长度和无线硬件CRC参数。

## 4. 摄像头板相关引脚

### 4.1 CX93510 SPI

- SCK：P0.12。
- MOSI：P0.14。
- MISO：P0.15。
- CS/HSS：P0.16。
- SPI模式：Mode 0。
- SPI频率：8 MHz。
- PD_RAM：P0.11，高电平启用CX93510帧缓冲RAM。

### 4.2 OV7676和指示灯

- OV7676 XSHUTDOWN：P0.06；先拉低复位/关断，再拉高进入工作状态。
- 图像发送指示灯：P0.08，高电平点亮。
- 开始发送一帧图像时点亮，配置块和JPEG块发送完成后熄灭。

## 5. OV7676配置

OV7676不是直接连接到nRF的I2C外设，而是由nRF通过SPI操作CX93510，再使用CX93510内部I2C主机访问OV7676。每次代理I2C操作都有完成状态、ACK和超时检查。

初始化顺序：

1. P0.06拉低，使OV7676进入XSHUTDOWN。
2. 等待5 ms后将P0.06拉高，等待时钟和I2C接口稳定。
3. 读取`0x300A/0x300B`，芯片ID必须为`0x7676`。
4. 写入经过量产验证的完整寄存器表。
5. 写`0x5009=0x00`，锁定Y0/U/Y1/V字节顺序。
6. 写`0x0100=0x01`，启动连续视频输出。
7. 等待60 ms，使AE、AWB和ISP开始稳定。
8. 回读关键寄存器，检查输出使能、尺寸、格式和YUV顺序。

关键配置：

| 功能 | 寄存器 | 配置 | 作用 |
|---|---:|---:|---|
| 软件复位 | `0x0103` | `0x01` | 恢复传感器基础状态 |
| 同步输出使能 | `0x3001` | `0x07` | 允许同步信号输出 |
| 数据输出使能 | `0x3002` | `0xFF` | 允许D0-D7输出 |
| 输出宽度 | `0x3808/09` | `0x01E0` | 480像素 |
| 输出高度 | `0x380A/0B` | `0x01E0` | 480像素 |
| 输出格式 | `0x4308` | `0x04` | YUV422 |
| YUV顺序 | `0x5009` | `0x00` | Y0/U/Y1/V |
| 流启动 | `0x0100` | `0x01` | 开始连续输出帧 |

其余寄存器包括内部时钟、曝光、增益、白平衡、黑电平、颜色处理和镜头补偿参数，保持量产配置值。旧表中位于`0x5804..0x580A`连续区域的`0x2809`按上下文修正为`0x5809`。

## 6. CX93510配置

### 6.1 接口检测

1. 初始化8 MHz SPI并预先将CS/HSS保持高电平。
2. P0.11拉高，启用帧缓冲RAM。
3. CX93510上电后的第一次SPI事务用于接口自动识别，随后再次读取器件信息。
4. `SLAVE_SEL`低两位必须为`01`，表示已进入SPI从机模式。
5. 读取`PN_BO_REV`确认器件和修订版本。

### 6.2 OV7676代理I2C

- 设备地址：`0x78`。
- 传感器寄存器地址：16位。
- 数据：8位。
- I2C时钟：约400 kHz。
- 每次读写都等待`XFER_IN_PROG`清零，并检查`RACK`。

### 6.3 并行图像输入

| CX93510寄存器 | 值 | 说明 |
|---|---:|---|
| `SI_CFG_1` | `0x24` | 垂直同步参考极性及YUY2字节顺序 |
| `SI_CFG_3` | `0x01` | 有限采集一帧 |
| `H_ACT` | `0x00` | 水平有效区配置 |
| `H_CAP_DLY` | `0x00` | 水平采集延迟 |
| `H_CAP_WIDTH` | `0x3C` | 60 x 8 = 480像素 |
| `V_CAP_DLY` | `0x00` | 垂直采集延迟 |
| `V_CAP_HEIGHT` | `0x3C` | 60 x 8 = 480行 |

### 6.4 JPEG编码器

- `DIFF_JPEG_CTRL.bit0=0`：关闭差分JPEG，使用直接帧模式。
- `JPEG_ENC_DCT_LM=0x00`：亮度使用标准量化表。
- `JPEG_ENC_DCT_CH=0x01`：色度使用标准量化表。
- `JPEG_ENC_CTL1.RELOAD_TABLES=1`：压缩器复位后重新加载量化表和Huffman表。

`RELOAD_TABLES`必须置1。否则帧缓冲可能只产生`0x10`图像块，而没有包含DQT/DHT的`0x40`配置块，标准Qt JPEG解码器会报告“Quantization table 0x00 was not defined”。

## 7. 单帧采集过程

每次采集按以下顺序执行：

1. 设置`DIFF_JPEG_CTRL.RST_COMP`，复位JPEG压缩器和帧缓冲写指针。
2. 等待`JPEG_DEC_STAT3.INIT_DONE=1`。
3. 清除`RST_COMP`。
4. 设置`JPEG_ENC_CTL1.RELOAD_TABLES=1`。
5. 写`SI_CFG_3=0x01`，要求采集一帧。
6. 写`SI_CFG_2=0x80`，启动有限帧采集。
7. 轮询`SI_CFG_2.EN_LFC`；硬件完成一帧后自动清零。
8. 前端完成后继续等待JPEG编码器将状态QWORD提交到帧缓冲。
9. 扫描帧缓冲，取得配置块和图像块的地址与长度。

采集、JPEG编码和帧缓冲写入不是同时结束的，因此代码在前端完成后额外等待有效状态QWORD，避免偶发读到全零头。

## 8. CX93510帧缓冲结构

每个数据块前面都有8字节状态QWORD。状态QWORD的高半字节表示块类型，最后两字节表示随后数据的有效长度。块数据按8字节边界填充。

正常直接JPEG采集产生两个块：

```text
地址0
  8字节状态QWORD：flags=0x40，size=688
  688字节JPEG配置：SOI + DQT + DHT + EOI

地址696 = 8 + 688
  8字节状态QWORD：flags=0x10，size=实际JPEG扫描块长度
  JPEG图像块：SOI + SOF0 + SOS + 压缩数据 + EOI
```

Qt最终合成时：

1. 去掉配置块末尾的EOI。
2. 去掉图像块开头重复的SOI。
3. 将剩余两部分连接，得到标准JPEG：`SOI + DQT + DHT + SOF0 + SOS + 数据 + EOI`。

## 9. 254字节图像包协议

每个Radio包固定254字节，不使用可变长度字段：

| 字节位置 | 长度 | 字段 | 说明 |
|---:|---:|---|---|
| 0-2 | 3 | Magic | ASCII `IMG`，即`49 4D 47` |
| 3 | 1 | Version | 当前为`0x01` |
| 4 | 1 | Flags | 块类型和首尾标志 |
| 5 | 1 | Payload length | 本包实际载荷长度，1-236 |
| 6-7 | 2 | Frame ID | 帧编号，小端，每次成功采集后加1 |
| 8-9 | 2 | Fragment index | 当前分片编号，小端，从0开始 |
| 10-11 | 2 | Fragment count | 当前数据块的分片总数，小端 |
| 12-15 | 4 | Block size | 当前配置块或JPEG块的总字节数，小端 |
| 16-251 | 236 | Payload/padding | 图像载荷；末包不足部分补0 |
| 252-253 | 2 | CRC16 | 前252字节的CRC，小端 |

Flags定义：

| 位 | 值 | 含义 |
|---:|---:|---|
| bit0 | `0x01` | 当前块第一个分片 |
| bit1 | `0x02` | 当前块最后一个分片 |
| bit2 | `0x04` | JPEG配置块（0x40块） |
| bit3 | `0x08` | JPEG图像块（0x10块） |
| bit4 | `0x10` | 兼容旧版独立JPEG布局；正常0x40+0x10模式不使用 |

CRC算法为CRC-16/CCITT-FALSE：

- 多项式：`0x1021`。
- 初始值：`0xFFFF`。
- 输入不反射。
- 输出不反射。
- 最终异或值：`0x0000`。
- CRC覆盖字节0-251，包括末包未使用的零填充区域。

无线外设自身还启用了16位硬件CRC，用于检查空中传输。包尾应用CRC用于继续保护nRF到STM、STM到电脑两段UART链路。

## 10. 分片数量计算

每个协议包最多携带236字节配置或图像数据：

```text
fragment_count = ceil(block_size / 236)
```

例如一帧日志为：

```text
配置块：688字节
JPEG块：15930字节
```

则：

```text
配置分片 = ceil(688 / 236) = 3包
JPEG分片 = ceil(15930 / 236) = 68包
整帧逻辑包数 = 3 + 68 = 71包
```

默认单次发送时实际发送71个Radio包。打开重复发送宏后，配置块和JPEG块各完整发送两遍，实际发送142包，但逻辑分片数量仍是71；接收端不会把重复包追加到图像中。

## 11. 发送调度和宏配置

图像发送参数位于摄像头角色的`main.c`顶部：

```c
#define IMAGE_PERIOD_MS           250u
#define IMAGE_FRAGMENT_GAP_MS     1u
#define IMAGE_REPEAT_SEND_ENABLED 0
#define IMAGE_PASS_GAP_MS         20u
```

### 11.1 当前默认：只发送一次

```c
#define IMAGE_REPEAT_SEND_ENABLED 0
```

发送顺序：

```text
配置片0 -> 配置片1 -> 配置片2
-> JPEG片0 -> JPEG片1 -> ... -> JPEG片N-1
```

### 11.2 可选：完整重复两遍

```c
#define IMAGE_REPEAT_SEND_ENABLED 1
```

发送顺序：

```text
配置片0..2 -> 等待20ms -> 配置片0..2
-> JPEG片0..N-1 -> 等待20ms -> JPEG片0..N-1
```

两个副本的帧号、块类型、分片号、载荷和CRC完全一致。Qt使用字典按分片编号保存，已经收到的重复分片不会覆盖或重复追加。

### 11.3 250 ms周期的含义

TIMER1每1 ms中断一次，每累计250 ms设置一次采集请求标志。真正的采集和SPI读取在主循环中进行，不在定时中断内执行。

如果上一帧在下一个250 ms时刻仍未发送完，程序输出：

```text
Image period skipped: previous frame still transmitting
```

并跳过本次请求，避免CX93510帧缓冲覆盖正在发送的数据。因此250 ms是请求间隔，实际帧率还受JPEG大小、分片间隔、无线发送耗时和是否重复发送影响。

## 12. 发送状态机

1. 定时器设置`m_capture_due=true`。
2. 主循环确认上一帧已经结束。
3. 调用`cx93510_capture_one()`采集一帧。
4. 帧号加1，首先选择688字节配置块。
5. P0.08拉高，表示图像开始发送。
6. 每次主循环到达计划时间时，读取最多236字节CX93510帧缓冲。
7. 填写16字节协议头和零填充区。
8. 计算前252字节CRC16，写入包尾。
9. Radio发送254字节，完成后立即恢复接收状态。
10. 配置块结束后自动切换到JPEG块。
11. JPEG块结束后P0.08拉低，并清除发送活动状态。

发送状态机每次只处理一个分片，不会在TIMER1或Radio中断中执行SPI读取和日志打印。

## 13. 专用nRF接收板

- `APP_ROLE_DEDICATED_RECEIVER=1`。
- P0.23始终输出低电平，选择硬件接收模式。
- Radio中断检查无线硬件CRC并将正确包复制到环形队列。
- 主循环从队列取出固定254字节包，通过1 Mbps UART发送。
- UART RX=P0.16，UART TX=P0.15。
- 不解析、不修改、不去重图像包。
- RTT日志和UART二进制流使用不同通道，不会互相污染。

## 14. STM32桥接

- USART2通过DMA循环模式接收nRF数据。
- DMA缓冲区数据批量转存到10240字节软件环形缓冲区。
- 主循环搜索`IMG 01`包头并收集固定254字节候选包。
- 检查协议字段和包尾CRC16。
- CRC错误包不发送给电脑，等待重复发送的正确副本；单次发送模式下，该帧会显示缺片。
- 合法包通过USART1以1 Mbps原样发送给电脑。
- STM不进行分片去重和JPEG合成。

## 15. Qt接收和图像重组

1. 在串口混合流中搜索`49 4D 47 01`。
2. 取得固定254字节候选包。
3. 验证结构字段和CRC16。
4. 按`Frame ID + 块类型 + Fragment index`保存分片。
5. 使用`setdefault`忽略重复副本。
6. 配置块和JPEG块全部收齐后按分片编号连接。
7. 合成标准JPEG。
8. 先写入`frame_xxxxx.jpg`，再交给Qt显示。

状态栏中的`CRC错误`表示STM到电脑这一段发现的内容错误。STM若在前一段UART已经发现CRC错误，会直接丢弃该包，并通过文字日志输出累计拒绝数量。

## 16. 主要日志判断

正常CX93510采集：

```text
CX93510 FB block: address=0 flags=0x40 size=688
CX93510 FB block: address=696 flags=0x10 size=15930
```

正常单次发送：

```text
TX block: JPEG config, size=688, fragments=3
TX block: JPEG image, size=15930, fragments=68
Image n transmitted
```

单次发送模式不应出现：

```text
TX block repeat pass 2/2
```

Qt正常结果：

```text
开始帧 n：配置 688 字节 / 3 包
帧 n JPEG：15930 字节 / 68 包
帧 n 完整：71 包，合成 JPEG ... 字节
帧 n 已保存并显示
```

## 17. 相关文件

- `app_role.h`：选择摄像头发送角色或专用接收角色。
- `main.c`：250 ms调度、Radio配置、图像协议、分片和发送状态机。
- `spi_bus.c/.h`：nRF52832与CX93510的SPI底层传输。
- `cx93510.c/.h`：CX93510初始化、代理I2C、JPEG采集和帧缓冲读取。
- `ov7676.c/.h`：OV7676上电、量产寄存器表、关键配置回读。
- `my_stm_ov7766/Core/Src/image_bridge.c`：STM32 DMA接收、定帧、CRC检查和透传。
- `my_stm_ov7766/Tools/serial_image_receiver.py`：Qt串口接收、去重、重组、保存和显示。
